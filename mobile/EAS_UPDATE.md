# Remote updates

The SDK 54 app uses `expo-updates` with EAS project
`7148323b-502c-447e-96c3-a5c1704c40c9`. The dynamic `app.config.js` is authoritative:
updates use `https://u.expo.dev/7148323b-502c-447e-96c3-a5c1704c40c9`, and the runtime
version is generated from native dependencies/configuration (`fingerprint` policy).

## One-time rollout

Existing binaries built without `expo-updates` cannot receive OTA updates. After
merging, create and install a new preview build, then ship a new production build
through the existing store release process. Check the latest store build number
before building. The production profile increments the iOS build number.

From `mobile/`:

```sh
npx --yes eas-cli@25.3.0 build --profile preview --platform ios
# Or --platform android. iOS internal distribution needs registered devices.
```

`preview` builds subscribe to the `preview` channel and EAS environment;
`production` builds subscribe to `production`. The `development` and `development-device` channels are CLI-generated labels;
development clients use their normal Extensions/Metro workflow, not release
automatic startup updates. Publishing there does not make dev clients auto-update. Both release environments currently use the live
LedgerCraft API, so preview is not a separate backend sandbox.

## Publish a compatible change

Run mobile lint, TypeScript, Jest and platform exports before publishing. Commit
and review the exact changes to publish. From `mobile/`:

```sh
npm run update:preview -- --message "Describe the fix"
# Verify on the installed preview binary before publishing production.
npm run update:production -- --message "Describe the verified fix"
```

These commands publish both iOS and Android bundles using explicitly selected
EAS environments. They do not build or submit a store binary. EAS Update does
not inherit `build.<profile>.env` from `eas.json`: keep `EXPO_PUBLIC_API_URL`,
`EXPO_PUBLIC_APP_ORIGIN`, and `EXPO_PUBLIC_SENTRY_DSN` in the matching EAS
environments. Check them with `npx --yes eas-cli@25.3.0 env:list --environment
production` (or `preview`). Never put secrets in `EXPO_PUBLIC_*` variables.
Local production publishing requires `SENTRY_AUTH_TOKEN`; it exports source maps,
uploads them to Sentry, and only then publishes the same bundle with the pinned
EAS CLI 25.3.0. A missing token or failed upload stops publication. Add
`--platform ios` to publish only the TestFlight platform. Preview uploads maps
when a token is available.

For the existing EAS-only secret, use the manually dispatched cloud workflow:

```sh
npx --yes eas-cli@25.3.0 workflow:run .eas/workflows/update-ios-production.yml -F message="Describe the verified iOS fix"
```

The workflow requires monitoring configuration before publishing, targets iOS
production, and requires Sentry source-map upload. Expo manages the job tooling
version. Unlike the local script, the managed job uploads maps after publication:
a failed upload fails the job but does not retract the OTA. Inspect the published
group and retry the upload or roll back before calling the release successful.

JavaScript, styling and bundled assets can update without a store release.
Native dependency, SDK, permission, entitlement or configuration changes produce a
new fingerprint and require new binaries. JavaScript-only changes retain the
native runtime. Never override a fingerprint to force an incompatible update.
`app.json` owns the app version and iOS build number; dynamic config reads them,
and tests enforce consistency. Store versioning is separate from runtime matching.

## Update signing

Updates currently rely on EAS account authorization and HTTPS; no independent
update-signing certificate is embedded. This means a compromised publish-capable
EAS credential could publish JavaScript. This remains an explicit limitation;
keep publish tokens scoped to the project/release automation, restrict publisher
access, and rotate exposed tokens. Do not put publishing credentials in the app.
Enabling Expo update code signing requires a separately managed private key and
certificate rollout in a new binary; no signing keys are generated by this change.

## Device verification and recovery

The default update behavior checks on cold launch, downloads in the background,
and applies on a subsequent restart. It does not reload during invoice editing.
Fully close and reopen the release app, allow time for download, then fully
close and reopen again. Verify the visible change, login, API reads/writes and
an offline relaunch. Expo Go and development-client checks do not prove the
release startup flow.

Confirm the published group in EAS matches the build's project, channel, runtime
and platform. Record the group ID, build ID and device result with release
evidence. See the release evidence below for the current verification status.

If a published update regresses, use the EAS dashboard to republish a known-good
update for the same runtime, or use `eas update:republish` following its current
`--help`. If necessary, use EAS's rollback-to-embedded flow for the affected
runtime. A Git revert alone does not withdraw an already published update.
Do not disable Expo's anti-bricking measures or bypass runtime compatibility.

References: [setup](https://docs.expo.dev/eas-update/getting-started/),
[runtime versions](https://docs.expo.dev/eas-update/runtime-versions/),
[rollback](https://docs.expo.dev/eas-update/rollbacks/).
